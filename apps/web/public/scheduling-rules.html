Schedule Solver Rules

This document explains the scheduling rules currently applied by the Schedule Solver product. It separates what schedulers see in the UI and API from what the solver enforces when it generates a draft.

Current as of 2026-05-13. Source areas: schedule workspace, API schemas and routes, provider eligibility service, solver contracts, solver implementation, fairness service, and project docs.

Rule Severity

Severity Meaning Publish behavior
Hard The assignment is not allowed for a published schedule. The API rejects publish with HTTP 409.
Warning The assignment or schedule should be reviewed, but the backend treats it as publishable. The API does not reject publish for warning-only issues.
Soft The solver uses the rule as a scoring preference when choosing among valid schedules. Soft rules do not block publish.

Current UI nuance: the Schedule constraints table counts only hard rows as publish blockers, but the client-side publish handler currently treats any selected Provider status other than valid as not publishable. That means a UI warning can prevent the button flow even though the API publish endpoint only blocks hard violations.

UI And API Rules

Schedule Periods

  • A Schedule Period has a name, start date, end date, and status.
  • The API rejects a period whose end date is before the start date.
  • The current availability workflow treats a Schedule Period as a schedule week.
  • Deleting a Schedule Period removes its versions, assignments, violations, schedule jobs, fairness records, and weekly availability rows.

Rooms, Room Types, And MD-Only Slots

  • Only active Centers can receive new Rooms.
  • Only active Rooms are listed for scheduling.
  • Rooms can require one or more Room Types.
  • Each Room Type requirement currently uses proficiency level 1 when added through the room UI/API path.
  • An md_only Room requires the assigned Provider to have provider type doctor.
  • If a Room has existing schedule records, deleting it deactivates it instead of removing the row.

Providers, Credentials, And Skills

  • Only active Providers are returned by the Providers API and shown in the scheduling UI.
  • Provider type must be one of crna, doctor, staff, contractor, or other.
  • Employment type must be one of employee, contractor, locum, or other.
  • Credentialed Center IDs must point to active Centers in the same organization.
  • Room Type skill IDs must point to active Room Types in the same organization.
  • Duplicate credentialed Center IDs and Room Type skill IDs are collapsed before saving.
  • Provider Center Credentials can also carry active, start, and expiration fields in the database. The eligibility service uses those fields when present.

Weekly Availability

  • Availability is stored per Provider, Schedule Period, and weekday.
  • Every replace request must contain exactly seven day rows.
  • Each weekday must appear exactly once.
  • Allowed options are full_shift, first_half, second_half, short_shift, none, and unset.
  • Each day must have at least one option.
  • unset cannot be combined with any other option.
  • none cannot be combined with any other option.
  • Work options can be combined with each other.
  • Min and max requested shifts must be between 0 and 14.
  • Min requested shifts must be less than or equal to max requested shifts.
  • The backend rounds min and max requests to the nearest half shift before validation.
  • The backend validates min and max against available half-shift units: full-shift days count as two units, half/short days count as one unit.
  • The frontend validates min and max against the count of work-available days, so it can be stricter than the backend for half-shift values.
  • Reading missing availability returns weekday defaults: weekdays default to unset, weekends default to none.
  • Saving a day with only unset stores that day as none.
  • Published schedule weeks lock availability edits. The API rejects replace and delete with HTTP 409.

Provider Eligibility

The backend Provider eligibility service is the main rule engine for manual assignment, saved draft validation, publish validation, and solver candidate generation.

Overlap Exception

A Provider may overlap a first_half assignment with a second_half assignment only when both assignments are in the same Center. Other overlaps are hard violations.

Full-Shift Accommodation

full_shift availability can cover a shorter slot type. This is treated as eligible with a warning, not as a hard violation.

Manual Scheduling Flow

Provider Picker

  • The UI computes local eligibility so the picker can show eligible Providers first.
  • The UI shows ineligible Providers with reason text instead of hiding them.
  • The UI calls POST /schedule-provider-eligibility when a Provider is selected.
  • Backend reasons are merged with local reasons after selection.
  • Double-booked Provider options are disabled in the picker.
  • Other hard-ineligible Provider options remain visible and can be selected, but the slot becomes invalid.
  • If backend eligibility verification fails, the UI adds provider_eligibility_check_failed as a hard reason.

Draft Save

  • Saving a draft creates a new immutable Schedule Version.
  • Saving does not mutate older Schedule Versions.
  • Assignments may have a null Provider so incomplete drafts can be preserved.
  • Unassigned slots do not create draft constraint violations.
  • Assigned Providers are validated through backend eligibility during draft save.
  • All eligibility violations and warnings from assigned Providers are persisted as Constraint Violations.
  • Shift-request warnings are also created for active Providers with availability rows.
  • If the draft has a parent version, slot dates are preserved from the parent unless allow_slot_date_change is true.
  • Fairness snapshots and events are recorded for saved versions.

Publish

  • Publishing always re-runs Provider eligibility against current backend data.
  • Publishing treats unassigned slots as hard violations.
  • The API rejects publish when any hard violation exists.
  • The API allows publish when only warning-level issues exist.
  • Publishing marks the chosen Schedule Version as published.
  • Other published versions for the same period are marked superseded.
  • The Schedule Period is marked published.
  • Published schedules rebuild the published fairness ledger.

Solver Rules

The solver generates draft Schedule Versions. It never publishes a schedule directly. It uses Google OR-Tools CP-SAT for assignment decisions.

Solver Inputs

  • Organization ID and Schedule Period ID.
  • Rooms and their active status, MD-only flag, Center, and required Room Type skills.
  • Providers and their active status, provider type, Room Type skills, weekly availability, preferences, and fairness state.
  • Provider Center Credentials.
  • Shift Requirements inside the Schedule Period.
  • When the UI sends current board assignments to generation, those assignments become solver shift requirements with a locked Provider when one is already selected.

Candidate Generation

  • The solver first builds valid Provider/shift candidates.
  • If a shift has a locked Provider, only that Provider can be a candidate.
  • If a shift references a missing Room, no candidates are produced for that shift.
  • If a shift references an inactive Room, no Provider is eligible for that shift.
  • Provider candidates must pass the same backend eligibility evaluator used by manual scheduling.
  • The solver does not create decision variables for hard-ineligible Provider/shift combinations.
  • If a shift has fewer candidates than its required Provider count, generation is infeasible.
  • If no shift requirements exist, generation is infeasible with missing_shift_requirements.

Hard Solver Constraints

  • Every shift requirement must receive exactly required_provider_count assignments.
  • A Provider cannot be assigned to overlapping shifts unless the split-day same-Center exception applies.
  • Missing or inactive Rooms cannot be assigned.
  • Inactive Providers cannot be assigned.
  • Provider type requirements must match.
  • Center credentials must exist and be active for the shift time.
  • Required Room Type skills and proficiency levels must be satisfied.
  • MD-only Rooms require a Provider type of doctor.
  • Availability must exist and must not be unset or none.
  • The shift type must be available, except full-shift availability can cover shorter shifts with a warning.

Solver Objective

After hard constraints are satisfied, the solver chooses the highest-scoring schedule using weighted objective terms.

Objective term Current behavior
Minimum shift requests Penalizes falling below min_shifts_requested.
Maximum shift requests Penalizes going above max_shifts_requested.
Assignment balance Penalizes differences in assignment totals between Providers.
Fairness pressure Applies stronger penalty to assigning Providers with higher fairness pressure.
Provider Center preference Adds score for matching active Provider Center preferences.
Provider shift-type preference Adds score for matching active Provider shift-type preferences.
Manager hidden Center preference Adds score for matching active manager Center preferences.

Solver Output

  • A feasible run creates a draft Schedule Version with source solver.
  • Solver assignments are persisted as draft Assignments.
  • Single-provider shifts reuse the shift requirement room slot ID.
  • Multi-provider shifts receive distinct deterministic room slot IDs for each assignment.
  • Warnings are persisted as Constraint Violations.
  • Infeasible runs persist a draft version with violations and no assignments, then the API responds with HTTP 409.
  • Unfillable shifts use unfillable_shift_requirement.
  • An unsatisfied CP-SAT model uses infeasible_solver_model.
  • Solver metrics include solve duration, payload size, the too-long threshold, and whether that threshold was exceeded.

Fairness Rules

Fairness is recorded for saved and generated drafts, and the published fairness state is rebuilt after publish. It is also part of the solver objective.

  • Below minimum shift request creates a debt event.
  • Above maximum shift request creates a debt event.
  • Full-shift availability used for a shorter shift creates a debt event.
  • Under-average workload creates favor credit.
  • Existing debt and favor credit decay before current schedule events are applied.
  • Provider priority tier changes the pressure multiplier.
  • Higher fairness pressure makes the solver less likely to assign that Provider when alternatives satisfy hard constraints.

Known Rule Mismatches To Watch

  • The API allows warning-only publish, but the UI publish handler can block warning statuses.
  • The frontend availability form validates min and max requested shifts by work-day count, while the backend validates using half-shift units.
  • The availability API stores a day submitted as only unset as none.
  • Manual UI assignments currently send required_provider_type as null, so provider-type matching applies mainly to saved assignments or solver shift requirements that carry that field.
  • Solver shift requirements loaded from stored shift_requirements currently use full_shift as their shift type.
